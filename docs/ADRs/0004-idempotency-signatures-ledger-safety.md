# ADR 0004: Transaction Integrity, Signature Verification, and Ledger Safety

## Status
Approved

## Context
Payment processing and ledger balance updates are highly sensitive operations prone to duplicate submissions, data interception, and race conditions. In Burger Farm, we need to guarantee that:
1. Customers are never charged twice for the same order checkout request.
2. Webhooks from Stripe are authentic and not spoofed by local client-side API injection attacks.
3. Loyalty reward points earned or redeemed are resilient against double-spending when users click concurrently on multiple devices.

## Decision
We enforce three architectural security patterns:

### 1. Deterministic Idempotency Keys (Stripe & Redis)
*   **Implementation**: Every checkout payload carries a deterministic `X-Idempotency-Key` header generated by hashing the Cart ID and User ID.
*   **Mechanism**: The server queries Redis using `SETNX` (Set if Not Exists) with a 24-hour TTL. If the key exists, the request returns the cached response instead of charging the card again.

### 2. Cryptographic Webhook Signatures (HMAC SHA-256)
*   **Implementation**: Rather than relying on client callbacks, the server handles Stripe callbacks asynchronously via signed webhooks.
*   **Mechanism**: The server calculates the HMAC SHA-256 digest of the request body using the webhook endpoint secret and performs a constant-time string comparison against the `Stripe-Signature` header to authorize the payment state write.

### 3. Double-Entry Append-Only Loyalty Ledger with Optimistic Concurrency Control (OCC)
*   **Implementation**: We reject mutable points balance columns in the database. Instead, every earn or redeem action is recorded as an immutable row in the `LoyaltyTransaction` table.
*   **Mechanism**: To prevent concurrent balance double-spend, the User record maintains a `version` integer. Balance deductions are validated using OCC: `UPDATE User SET balance = balance - X, version = version + 1 WHERE id = ? AND version = ?`.

## Alternatives Considered
*   *Client-Side Checkout Callbacks*: Easily intercepted and spoofed via proxy inspect tools. Rejected for absolute server-to-server webhook confirmation.
*   *Mutable Points Column (No Ledger)*: Prone to write skew, silent balance corruption, and lacks transaction log audit trail. Rejected.

## Tradeoffs
*   **Complexity**: Adds concurrency checking logic (OCC) and caching layers (Redis keys).
*   **Latency**: Minor cryptographic signature verification compute time (<2ms) on webhooks.
*   **Safety**: Zero double-spend anomalies, complete audit transparency, and resilient payment gateway integration.
