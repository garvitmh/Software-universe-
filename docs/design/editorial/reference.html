Cross-cutting logic · Entry 14

Caching

Keeping the answer close, so you needn't ask the slow thing twice.

The analogy
Your barista already knows your usual. They don't re-ask every morning — they keep it close. A cache is that memory for your software.

§1What it is

A cache stores copies of expensive answers. The first time you ask, the system does the slow work — a database query, an API call — and tucks the result away. The next time, it returns the stored copy. We call the first a cache miss and the second a cache hit. More hits means lower latency.

§3How it works

The pattern is get-or-set. Ask the cache first. On a hit, return it. On a miss, do the real work, store it with a TTL, and return it.

async function getUser(id) {
  const hit = await cache.get(`user:${id}`);
  if (hit) return hit;            // cache hit
  const user = await db.users.find(id);  // slow work
  await cache.set(`user:${id}`, user, { ttl: 60 });
  return user;
}

§4Why it's built this way

Databases are correct but comparatively slow. A cache trades a little freshness for a great deal of speed. The alternative — asking the database every single time — is simpler and always fresh, but falls over under load. Caching is the first lever you pull when reads outnumber writes.

When it breaks
  • Stale data. A copy lives past its usefulness — users see an old price. TTLs and invalidation fight this.
  • Thundering herd. A popular key expires and thousands of requests hit the database at once — a thundering herd.
  • Eviction surprises. Memory fills, the LRU policy drops the very thing you needed.
